Hetzner setup — Step 1: Provision the server

If you don't already have an SSH keypair, generate one first (on your own machine):

    ssh-keygen -t ed25519 -C "guardbox-site"

That gives you ~/.ssh/id_ed25519.pub — you'll paste that public key into Hetzner in a moment.

Then in the Hetzner Cloud Console (https://console.hetzner.cloud):

1. Create a new project (or use an existing one) -> Add Server.
2. Location: Falkenstein or Nuremberg (Germany) — keeps it EU-resident, consistent with everything else.
3. Image: Ubuntu 24.04 LTS.
4. Type: cheapest shared vCPU tier (currently their entry Cloud VPS, e.g. CX22 or equivalent) — plenty for a static site + one small endpoint.
5. SSH key: paste your public key (cat ~/.ssh/id_ed25519.pub) here instead of setting a password — key-only access from the start.
6. Create it, and note the server's public IP once it's up.

Once you've got the IP and can `ssh root@<IP>` into it, move on to Step 2 — hardening.

Step 2: Harden the server

Keep the first SSH session open throughout — don't close it until the new setup is confirmed working.

    # 1. SSH in as root
    ssh root@<SERVER_IP>

    # 2. Update packages
    apt update && apt upgrade -y

    # 3. Create a non-root sudo user
    adduser deploy
    usermod -aG sudo deploy

    # 4. Copy SSH key to the new user
    rsync --archive --chown=deploy:deploy ~/.ssh /home/deploy

Open a SECOND terminal (leave root session running) and confirm the new user works:

    ssh deploy@<SERVER_IP>

Once that logs in successfully, back in the root session:

    # 5. Edit /etc/ssh/sshd_config — set:
    #    PermitRootLogin no
    #    PasswordAuthentication no
    nano /etc/ssh/sshd_config

    # 6. Restart SSH
    systemctl restart ssh

    # 7. Firewall — only SSH, HTTP, HTTPS
    ufw allow OpenSSH
    ufw allow 80/tcp
    ufw allow 443/tcp
    ufw enable

    # 8. Optional but recommended: fail2ban
    apt install fail2ban -y

Verify before moving on: `ssh root@<SERVER_IP>` should now FAIL, `ssh deploy@<SERVER_IP>` should still work.

Step 3: Install Docker + Docker Compose

Run as deploy (with sudo):

    sudo apt-get update
    sudo apt-get install -y ca-certificates curl
    sudo install -m 0755 -d /etc/apt/keyrings
    sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
    sudo chmod a+r /etc/apt/keyrings/docker.asc

    echo \
      "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu \
      $(. /etc/os-release && echo "$VERSION_CODENAME") stable" | \
      sudo tee /etc/apt/sources.list.d/docker.list > /dev/null
    sudo apt-get update

    sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
    sudo usermod -aG docker deploy

Log out/back in, then verify:

    docker run hello-world
    docker compose version

Step 4: Cloudflare Origin Certificate + Full (strict) TLS

In the Cloudflare dashboard for guardbox.dev:
1. SSL/TLS -> Origin Server -> Create Certificate.
   - Let Cloudflare generate the private key and CSR (default option).
   - Hostnames: guardbox.dev, *.guardbox.dev
   - Validity: 15 years.
   - Click Create — it will show an Origin Certificate (PEM) and a Private Key. Copy both.

2. On the server, create the cert files (paste each value into nano when it opens):

    sudo mkdir -p /etc/ssl/certs /etc/ssl/private
    sudo nano /etc/ssl/certs/cloudflare-origin.pem
    # paste the Origin Certificate content, save (Ctrl+O, Enter, Ctrl+X)

    sudo nano /etc/ssl/private/cloudflare-origin.key
    # paste the Private Key content, save

    sudo chmod 644 /etc/ssl/certs/cloudflare-origin.pem
    sudo chmod 600 /etc/ssl/private/cloudflare-origin.key
    sudo chown root:root /etc/ssl/certs/cloudflare-origin.pem /etc/ssl/private/cloudflare-origin.key

   IMPORTANT: paste the private key directly into the server's nano session only —
   never paste it into chat/Claude or anywhere else. It's the one real secret in this whole setup.

3. Back in Cloudflare dashboard: SSL/TLS -> Overview -> set mode to "Full (strict)".
   This makes Cloudflare verify the origin's cert on every request, so the
   Cloudflare-to-server leg is encrypted and authenticated, not just edge-to-visitor.

This cert/key pair will be referenced by nginx in Step 5.

Step 5: Deploy site + subscribe endpoint via Docker Compose

NOTE: needs the actual exported static site files (HTML/CSS/JS) from Lovable's GitHub
sync dropped into site/. Deployed below with a placeholder page first so the pipeline
(nginx, TLS, subscribe endpoint) can be verified end-to-end before swapping in the real
site content.

Run as deploy on the server:

    mkdir -p /opt/guardbox-site/nginx /opt/guardbox-site/site /opt/guardbox-site/subscribe
    cd /opt/guardbox-site

    # Placeholder page (swap out once the real Lovable export is ready)
    cat > site/index.html <<'EOF'
    <!doctype html><html><body><h1>GuardBox — coming online</h1></body></html>
    EOF

    # nginx config
    #
    # Privacy/security headers below follow EFF's guidance for a trustworthy site:
    # HSTS + TLS everywhere, a CSP that blocks any script/font/frame this site
    # doesn't itself serve, no referrer leakage to third parties (incl. the
    # outbound Kickstarter link), no browser feature access this static site
    # has no reason to request, and no nginx version fingerprint in responses.
    # style-src allows 'unsafe-inline' only because the current templates use
    # inline style="" attributes — no <script> exists anywhere, so script-src stays 'none'.
    #
    # Access logs are kept in default combined format (source IP included) purely
    # for abuse/security investigation, as disclosed in privacy.html, and are
    # rotated out after 7 days by the logrotate config further down — not
    # retained indefinitely.
    cat > nginx/nginx.conf <<'EOF'
    server_tokens off;

    server {
        listen 80;
        server_name guardbox.dev;
        return 301 https://$host$request_uri;
    }

    server {
        listen 443 ssl;
        server_name guardbox.dev;

        ssl_certificate /etc/ssl/certs/cloudflare-origin.pem;
        ssl_certificate_key /etc/ssl/private/cloudflare-origin.key;

        add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
        add_header Content-Security-Policy "default-src 'self'; script-src 'none'; style-src 'self' 'unsafe-inline'; img-src 'self'; font-src 'self'; frame-ancestors 'none'; base-uri 'none'; form-action 'self'" always;
        add_header X-Content-Type-Options "nosniff" always;
        add_header X-Frame-Options "DENY" always;
        add_header Referrer-Policy "no-referrer" always;
        add_header Permissions-Policy "camera=(), microphone=(), geolocation=(), payment=(), usb=(), interest-cohort=()" always;

        root /usr/share/nginx/html;
        index index.html;

        location /api/subscribe {
            proxy_pass http://subscribe:8000/api/subscribe;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
        }

        location /api/contact {
            proxy_pass http://subscribe:8000/api/contact;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
        }

        location / {
            try_files $uri $uri/ /index.html;
        }
    }
    EOF

    # Log rotation — keep access/error logs only 7 days, consistent with the
    # short-retention claim in privacy.html. Nginx's docker image logs to
    # stdout/stderr by default (captured by `docker compose logs`); if you switch
    # to file-based logs (access_log /var/log/nginx/access.log;), add this
    # logrotate config on the host so they don't accumulate indefinitely:
    #
    #   sudo tee /etc/logrotate.d/guardbox-nginx <<'ROTATE'
    #   /var/log/nginx/*.log {
    #       daily
    #       rotate 7
    #       compress
    #       delaycompress
    #       missingok
    #       notifempty
    #   }
    #   ROTATE
    #
    # If staying on the default stdout/stderr logging, cap docker's own log
    # retention instead by adding to the nginx service in docker-compose.yml:
    #   logging:
    #     driver: "json-file"
    #     options:
    #       max-size: "10m"
    #       max-file: "7"

    # Minimal subscribe service
    cat > subscribe/requirements.txt <<'EOF'
    fastapi
    uvicorn[standard]
    pydantic[email]
    EOF

    cat > subscribe/main.py <<'EOF'
    from fastapi import FastAPI
    from pydantic import BaseModel, EmailStr
    from typing import Optional
    import json
    from pathlib import Path
    from datetime import datetime, timezone

    app = FastAPI()
    SUBSCRIBERS_FILE = Path("/data/subscribers.jsonl")
    CONTACTS_FILE = Path("/data/contacts.jsonl")

    class SubscribeRequest(BaseModel):
        email: EmailStr

    class ContactRequest(BaseModel):
        name: str
        email: EmailStr
        company: Optional[str] = None
        role: str
        message: str

    @app.post("/api/subscribe")
    def subscribe(req: SubscribeRequest):
        SUBSCRIBERS_FILE.parent.mkdir(parents=True, exist_ok=True)
        with SUBSCRIBERS_FILE.open("a") as f:
            f.write(json.dumps({"email": req.email, "subscribed_at": datetime.now(timezone.utc).isoformat()}) + "\n")
        return {"status": "ok"}

    # Placeholder: appends to a file for now. Upgrade later to also send an SMTP
    # notification (e.g. via Proton Mail) once real mail is set up for the domain —
    # see the memory note on this migration for the full plan.
    @app.post("/api/contact")
    def contact(req: ContactRequest):
        CONTACTS_FILE.parent.mkdir(parents=True, exist_ok=True)
        with CONTACTS_FILE.open("a") as f:
            f.write(json.dumps({
                "name": req.name,
                "email": req.email,
                "company": req.company,
                "role": req.role,
                "message": req.message,
                "received_at": datetime.now(timezone.utc).isoformat(),
            }) + "\n")
        return {"status": "ok"}
    EOF

    cat > subscribe/Dockerfile <<'EOF'
    FROM python:3.12-slim
    WORKDIR /app
    COPY requirements.txt .
    RUN pip install --no-cache-dir -r requirements.txt
    COPY main.py .
    CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
    EOF

    # docker-compose.yml
    cat > docker-compose.yml <<'EOF'
    services:
      nginx:
        image: nginx:alpine
        restart: unless-stopped
        ports:
          - "80:80"
          - "443:443"
        volumes:
          - ./nginx/nginx.conf:/etc/nginx/conf.d/default.conf:ro
          - ./site:/usr/share/nginx/html:ro
          - /etc/ssl/certs/cloudflare-origin.pem:/etc/ssl/certs/cloudflare-origin.pem:ro
          - /etc/ssl/private/cloudflare-origin.key:/etc/ssl/private/cloudflare-origin.key:ro
        depends_on:
          - subscribe
        logging:
          driver: "json-file"
          options:
            max-size: "10m"
            max-file: "7"

      subscribe:
        build: ./subscribe
        restart: unless-stopped
        volumes:
          - subscriber-data:/data

    volumes:
      subscriber-data:
    EOF

    # Bring it up
    docker compose up -d --build

Test locally on the server before touching DNS:

    curl -k https://localhost/
    curl -k -X POST https://localhost/api/subscribe -H "Content-Type: application/json" -d '{"email":"test@example.com"}'
    docker compose exec subscribe cat /data/subscribers.jsonl

Getting the Lovable export onto the server

1. In the Lovable editor: toolbar GitHub button (or Settings -> GitHub) -> Connect to
   GitHub. Authorize Lovable's GitHub App — creates a repo with the full React/Vite
   source, kept in sync with future Lovable edits.

2. On your own machine (not the server), clone and build it:

    git clone <the-new-repo-url>
    cd <repo-folder>
    npm install
    npm run build

   This produces a dist/ folder — the static HTML/CSS/JS output. That's what goes on
   the server, not the React source.

    rsync -avz --delete ./dist/ deploy@<SERVER_IP>:/opt/guardbox-site/site/

4. Nginx is bind-mounted to that folder so it picks up new files immediately. To be safe:

    ssh deploy@<SERVER_IP> "cd /opt/guardbox-site && docker compose restart nginx"

    docker compose exec subscribe cat /data/subscribers.jsonl

IMPORTANT CORRECTION (found while verifying Step 6):

guardbox.dev's nameservers are still name.com's own (ns1-4.name.com), NOT Cloudflare's.
The Cloudflare dashboard used in Step 4 (origin cert, Full strict) is a SEPARATE zone/
account not actually in the DNS path. The live Cloudflare headers on the site are
Lovable's OWN backend infra, not our Cloudflare account. Editing DNS in "our" Cloudflare
dashboard had zero effect on live traffic — confirmed via curl: x-deployment-id header
and page content were still Lovable's after the attempted DNS change.

Decision: delegate name.com's nameservers to Cloudflare, so our Cloudflare zone becomes
actually authoritative, the origin cert + Full (strict) setup works as designed, and we
keep CDN/DDoS protection in front of the Hetzner origin.

Step 6 (revised): Delegate to Cloudflare, then cut over

1. In YOUR Cloudflare account: Add a site -> guardbox.dev.
   Cloudflare scans and imports existing DNS records automatically. BEFORE proceeding,
   review the imported record list carefully — make sure nothing gets missed (any TXT
   verification records for other services, etc.), since currently there's no MX/email
   records, but double-check anyway.

2. Cloudflare will show two nameservers to use (something like xxx.ns.cloudflare.com).

3. At name.com: go to the domain's REGISTRAR-level nameserver settings (not just DNS
   records — the actual "change nameservers" option) and replace the current
   ns1-4.name.com entries with the two Cloudflare-assigned nameservers.

4. Wait for propagation. This is slower than a normal record change — can take from
   under an hour up to ~24-48h in rare cases. Cloudflare's dashboard will show the zone
   status change from "Pending" to "Active" once it's picked up. Some inconsistency
   during this window is possible (different resolvers may briefly see old vs new NS) —
   expected, not a sign of a mistake.

5. Once the zone shows "Active" in Cloudflare: go to DNS records there, set the A
   record for guardbox.dev (and www if used) to the Hetzner server IP, Proxy status
   "Proxied" (orange cloud) ON.

6. Re-verify (same checks as before, from an external machine, not the server):

    curl -sI https://guardbox.dev/
    curl -s https://guardbox.dev/ | head -20
    dig +short guardbox.dev NS

   Confirm: NS now shows Cloudflare's nameservers, the x-deployment-id header is GONE
   (that was Lovable-specific), and the page content matches what's on the Hetzner
   server, not Lovable's.

7. Keep the Lovable project/domain binding as a rollback option for a day or two before
   fully decommissioning it.
